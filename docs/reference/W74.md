# W74 car-following contract (M3.3.3a)

Design before implementation, 2026-10-07 (D129). **No run uses it yet.** §3–§4 and the
§7 sign exist as the pure `w74Acceleration` in `src/core/w74.hpp` (D135, BA21–BA22,
[evidence](../evidence/w74-pure-function.md)); the tick does not call it. §5 and §9
are implemented (D136, BA29, [codec evidence](../evidence/w74-codec.md)), and §5's traits
(D137, BA26, [trait evidence](../evidence/w74-traits.md)): a schema-22 file
stores a `w74` behaviour, and Run refuses one that a vehicle type or road uses
(`UNSUPPORTED_BEHAVIOUR_MODEL_RUN`) until the rest of the M3.3.3a implementation lands
against the rows in [the delivery plan](../plans/DRIVING_BEHAVIOUR.md#3-failure-first-acceptance-rows)
(BA21–BA29). [DRIVING_BEHAVIOUR](DRIVING_BEHAVIOUR.md) owns assignment and
selection; [SIMULATION](SIMULATION.md) owns the shipped tick. This file owns the
`w74` model's equations, parameters, traits, state and model switch.

## 1. Scope and sources

TrafficSim's `w74` is a psycho-physical car-following model with the regime
structure Wiedemann published in 1974. It is our own explicitly parameterised
formulation, written from public sources only:

- PTV's public [Wiedemann 74 parameter page](https://cgi.ptvgroup.com/vision-help/VISSIM_2025_ENG/Content/4_BasisdatenSim/FahrverhaltensparameterFolgeverh_Wied74.htm)
  — vocabulary for `ax`, `bx_add`, `bx_mult` and the trait `z`.
- Eclipse SUMO's open [`MSCFModel_Wiedemann`](https://sumo.dlr.de/doxygen/dd/d8c/_m_s_c_f_model___wiedemann_8cpp_source.html),
  which cites Olstam & Tapani (2004, VTI) and Higgs et al. — the threshold set and
  the decision tree below follow its published structure.

It is **not** PTV's proprietary implementation and claims no equivalence with
Vissim or SUMO results. Values calibrated in Vissim do not transfer (rule 4); the
not-yet-validated marker stays. Out of scope: W99, bounded perception, attention,
amber decisions, lateral behaviour, motorcycles, calibration and PCU.

## 2. Inputs, units and gap convention

All quantities are SI: m, s, m/s, m/s². Per follower and tick, from the
pre-motion snapshot. The prototype receives `g` and `vL` only: today's `Leader`
is `{gap, speed}`. The implementation adds `Leader::acceleration`, and **every**
construction site fills it — the vehicle ahead from its snapshot `acceleration`,
every static obstacle (red head, dead end, priority/zone hold, courtesy at a
standing vehicle) with 0, cooperative braking with the changer's acceleration.
The prototype ignores the new field, so its results are unchanged.

| Symbol | Meaning |
|---|---|
| `v` | Follower speed |
| `vDes` | Sampled `desiredSpeed` |
| `g` | Net gap: the nearest standing-or-moving obstacle's rear minus the follower's front (the existing `Leader::gap`) |
| `vL`, `aL` | Obstacle speed and `Leader::acceleration` (new, above); a static obstacle has `vL = aL = 0` |
| `dv` | `v − vL` (positive = closing) |

Wiedemann writes thresholds on the gross distance including leader length. We
write them on the **net gap**, so `AX` below is a standstill net gap and no leader
length appears anywhere. This is a definitional shift, not a behavioural change.

## 3. Thresholds

With traits `zBx`, `zEx`, `zCx`, `zOp`, `zOsc` (§5) and `vBx = max(v, 0.1)` (PTV's minimum
speed under the root, so `BX > 0` at rest):

```
AX   = ax
BX   = (bxAdd + bxMult · zBx) · sqrt(vBx)
ABX  = AX + BX                                   desired minimum following gap
EX   = exAdd + exMult · zEx
SDX  = AX + EX · BX                              maximum following gap
CX   = cxAdd + cxMult · zCx
SDV  = ((g − AX) / CX)²   if g > AX, else 0      perception of approaching
CLDV = SDV · EX²                                 closing threshold
OPDV = −CLDV · (opdvAdd + opdvMult · zOp)        opening threshold (≤ 0)
DMAX = max(dMax, v² / (2 · type.comfortableDeceleration))
```

Validation guarantees `EX ≥ 1`, so `SDX ≥ ABX` and `CLDV ≥ SDV ≥ 0 ≥ OPDV`.

## 4. Regimes and accelerations

Classification, evaluated top to bottom; the first match wins:

| # | Condition | Regime | `FollowingMode` |
|---|---|---|---|
| 1 | No obstacle | free | `free` |
| 2 | `g ≤ ABX` | emergency | `braking` |
| 3 | `g < SDX` and `dv > CLDV` | approaching | `approaching` |
| 4 | `g < SDX` and `dv > OPDV` | following | `following` |
| 5 | `g < SDX` | free | `free` |
| 6 | `dv > SDV` and `g < DMAX` | approaching | `approaching` |
| 7 | otherwise | free | `free` |

Equality sides are part of the contract: `g = ABX` is emergency; `g = SDX` is
outside the following band; `dv = CLDV` is following, `dv = OPDV` is free;
`dv = SDV` is free; `g = DMAX` is free.

Accelerations (before §6's bounds):

- **Free.** `bMax = bMaxAdd + bMaxMult · max(0, bMaxSpeedRoot − sqrt(v))`. If
  `v ≥ vDes`, `a = 0` (the existing desired-speed cap does the rest). Otherwise,
  with an obstacle and `g ≤ 2 · ABX`, `a = min(bNull, bMax · (g − ABX) / ABX)`;
  else `a = bMax`.
- **Approaching.** `a = 0.5 · dv² / (ABX − g) + leaderAccelerationWeight · aL`,
  then `a ≥ −type.comfortableDeceleration`. Here `g > ABX`, so the first term is
  braking.
- **Following.** `a = s · bNull`, with `bNull = bNullAdd + bNullMult · zOsc` and
  the oscillation sign `s` from §7. Inside the band the driver keeps accelerating
  or decelerating until a threshold moves it to another regime.
- **Emergency.** If `g > AX`:
  `a = 0.5 · dv² / (AX − g) + emergencyLeaderWeight · aL + bMinAdd · (ABX − g) / BX`;
  else `a = −type.maxDeceleration`.
  The `dv²` term brakes even when the obstacle is pulling away (`dv < 0`), as in
  Wiedemann's and SUMO's form. A queued vehicle standing inside `ABX` therefore
  does not start until the gap exceeds `ABX`; this delays queue discharge and is
  model behaviour, recorded by BA23/BA27, not corrected here.

No regime uses a time constant, so `followingTime`/`speedThreshold` do not exist
on a `w74` behaviour.

## 5. Parameters and traits

### Parameters (hard rule 5: data, never code defaults)

A `model: "w74"` behaviour carries **every** key below; a missing, non-finite or
out-of-range value rejects the catalog/document atomically
(`INVALID_BEHAVIOUR_PARAMETER`, path to the key). Prototype keys
(`standstillDistance`, `additiveSafetyDistance`, `multiplicativeSafetyDistance`,
`followingTime`, `speedThreshold`) are rejected on a `w74` behaviour and W74 keys
on a prototype one (`EDIT_UNSUPPORTED_FIELD`); neither is an alias of the other.

| Key | Range | Role |
|---|---|---|
| `ax` | > 0 m | Standstill net gap `AX` |
| `bxAdd`, `bxMult` | `bxAdd > 0`, `bxMult ≥ 0` | `BX` coefficients (m per √(m/s)); `bxAdd > 0` keeps `BX > 0` when `zBx` clips to 0 |
| `exAdd`, `exMult` | `exAdd ≥ 1`, `exMult ≥ 0` | `SDX` spread |
| `cxAdd`, `cxMult` | `cxAdd > 0`, `cxMult ≥ 0` | Speed-difference perception scale |
| `opdvAdd`, `opdvMult` | `opdvAdd > 0`, `opdvMult ≥ 0` | Opening threshold |
| `dMax` | > 0 m | Far approaching horizon |
| `bMaxAdd`, `bMaxMult`, `bMaxSpeedRoot` | ≥ 0, `bMaxAdd > 0` | Free acceleration (m/s², m/s² per √(m/s), √(m/s)) |
| `bNullAdd`, `bNullMult` | `bNullAdd > 0`, `bNullMult ≥ 0` | Oscillation magnitude (m/s²) |
| `bMinAdd` | ≤ 0 m/s² | Emergency gap-deficit term |
| `leaderAccelerationWeight`, `emergencyLeaderWeight` | [0, 1] | Weight of `aL` |

Optional on `w74`: `maxDecelerationCooperativeBraking` (same meaning, a bound).
The discretionary keys (D95/D101) are refused on `w74` in this slice; A53 remains
failed and no W74 incentive is defined.

Type limits remain the type's: `maxAcceleration`, `comfortableDeceleration`,
`maxDeceleration`, length and desired-speed range. A shipped `w74` preset in
`data/driver-behaviour/` is a later slice; its values must cite their source and be
labelled uncalibrated.

### Driver traits

| Trait | Distribution | Source |
|---|---|---|
| `zBx` | Normal(0.5, 0.15) clipped to [0, 1] | The existing `driverFactor` — the same draw PTV calls `z`; no new stream draw |
| `zEx`, `zCx`, `zOsc` | Uniform [0, 1) | Hashed, indices 0, 1, 2 |
| `zOp` | `0.5 + 0.15 · (Σ₁₂ u − 6)` clipped to [0, 1] (Irwin–Hall) | Hashed, indices 3–14 |

Hashed traits never touch `SimState::randomState`, so legacy and mixed runs keep
their exact draw order (BA18):

```
mix(x)  = splitmix64 finaliser of x (Steele et al. constants)
h(i)    = mix(mix(seed) ^ (vehicleId · 0x9E3779B97F4A7C15) ^ i)
u(i)    = (h(i) >> 11) · 2⁻⁵³
zOp     = clip(0.5 + 0.15 · ((((u(3) + u(4)) + u(5)) + … + u(14)) − 6), 0, 1)
```

All integer arithmetic is on `std::uint64_t`, wrapping modulo 2⁶⁴ (`seed` is
widened from 32 bits first). `u(i)` is exact in a double. The Irwin–Hall sum adds
in ascending index order, left to right, as written; the build already disables
fast-math and contraction, so the rounding of each addition is fixed.

`seed` is `SimState::seed` (the run seed as given, before the zero remap). Only
integer operations, one multiply by 2⁻⁵³ and sums: no `log`/`cos`, so traits are
bit-identical across compilers. Traits are computed once, when the vehicle is
generated, and stored as `PendingVehicle::w74Traits`
(`std::optional<W74Traits>`), present iff the canonical scenario holds any `w74`
behaviour. They survive profile and model changes like `desiredSpeed` and
`driverFactor`, and are never redrawn while a record waits at its source.

**Implemented (D137).** `w74Traits(seed, vehicleId, driverFactor)` in `src/core/w74.hpp`;
`generateArrivals` stores it when `ScenarioIndex::w74` is set, so `upcomingArrivals`
(which copies the seed into its scratch state) predicts the same traits. Nothing reads them
until composition (BA28). `W74State` (§7) is added with that slice, the only writer.

## 6. Composition with the shipped tick

`w74` replaces only step 4's acceleration ([SIMULATION](SIMULATION.md#step-and-motion-a-vehicles-input-process-and-output)).
The result is clamped to `[−type.maxDeceleration, type.maxAcceleration]`, then:
D105 (a stopped vehicle with `g ≤ AX` gets no positive acceleration), ballistic
`integrate`, the `desiredSpeed` cap, the `allowedDistance` hard cap with counted
`safety-clamp`, Stop rest and phase-2 request resolution — all unchanged and
never weakened for a smoother-looking profile.

Per-model accessors replace direct reads of prototype fields:

| Accessor | Prototype | `w74` |
|---|---|---|
| `standstillGap(b)` | `standstillDistance` | `ax` |
| `desiredGap(b, vehicle, v)` | `standstill + (add + mult · driverFactor) · √v` | `ABX` at `v` |

Source insertion and D108, zone receiving space and waiting room, and
`stopLineReach` (`desiredGap` at `kStoppedSpeed` plus 0.1 m) read these. One
dispatcher `followingAcceleration(..., behaviour, ...)` serves every consumer:
own motion, the courtesy second obstacle, cooperative braking, lane-change own and
trailing checks, and the D108 first step. Hypothetical evaluations read the
vehicle's carried oscillation state but never write it.

## 7. State and model switch

```cpp
enum class W74Regime : std::uint8_t { free, approaching, following, emergency };
struct W74State { W74Regime regime; std::int8_t sign; };  // Vehicle::w74State, std::optional
```

The following regime's sign `s` is hysteresis on the previous tick's state:
`−1` after approaching or emergency (the driver was slowing), `+1` after free (it
was speeding up), and the stored `sign` after following. A tick in following
stores the `s` it used; other regimes store `sign = 0`.

**Standstill overrides the sign: in following with `v = 0`, `s = +1`.** A stopped
driver can only close up. Without this, a vehicle that brakes to rest in the
following band behind a static obstacle (`dv = 0` for ever) keeps `s = −1`, never
leaves the regime, and can rest farther than `stopLineReach` from a Stop line
that is then never served — a permanent standstill. With it the vehicle creeps
at `bNull` until `g ≤ ABX`, where emergency stops it with `AX < g ≤ ABX(0.1)`,
inside `stopLineReach` (BA28). D105 still forbids the creep when `g ≤ AX`.

**Two obstacles.** When motion evaluates a second obstacle (courtesy or
cooperative braking) and keeps the lower acceleration, as `stepSimulation` does
today, the stored regime and sign are those of the result kept; on equal
accelerations the vehicle ahead is kept, matching the existing strict `<`.
A later clamp, Stop rest or phase-2 shortening does not change the stored regime.

- **Entering `w74`** (no state, or the previous tick was prototype): initialise
  from the current snapshot, `s = dv > 0 ? −1 : +1`. No prototype memory is
  carried; the prototype has none.
- **Leaving `w74`**: the state is cleared at publish.
- **Re-entry** re-initialises. A boundary between two different `w74` behaviours
  keeps the state (the regime is model state, not parameter state).
- State is written only at publish, in vehicle-id order, from the regime chosen
  for the tick's own motion. It is copied with `SimState`, replays exactly, and is
  never read from `laneChangeTrace` or any display data.

Selection stays `effectiveBehaviour` ([§8](DRIVING_BEHAVIOUR.md#8-implemented-runtime-selection-m332b-d127)):
the front's segment at the pre-motion snapshot, up to one timestep of lag, no
within-tick switching. The obstacle's model never matters: a follower reads only
gap, speed and acceleration, so prototype→`w74` and `w74`→prototype leaders are
the same inputs.

## 8. Timestep and numerics

Regimes change only at ticks. Following accelerates by `±bNull` for a whole tick,
so the oscillation period depends on `dt ∈ (0, 0.5]`; the contract records that
sensitivity (BA27) rather than bounding it. Division guards are exact by
construction: `ABX − g < 0` in approaching, `AX − g < 0` and `BX > 0` in the
first emergency branch. No tolerance is introduced. The prototype's frozen
baselines and replay contracts are untouched: an unassigned or prototype-only
scenario compiles and runs byte-identically (BA18).

## 9. Persistence

Schema 25 is written only when some owned behaviour has `model: "w74"`; otherwise
schema 24 or earlier bytes are kept (22 is M5.3's evaluation period, D132; 23 is M5.4's
travel-time sections, D133; 24 is M5.5's section control type, D134). A file below 25 carrying `"w74"` is refused
(`UNSUPPORTED_BEHAVIOUR_MODEL`), as is any unknown model. External catalogs in
`data/driver-behaviour/` gain the same `model` key in that slice; an absent key
there continues to mean the prototype. Output checkpoints carry `w74Traits` and
`w74State` only when present.

**Implemented (D136).** The 18 key names live once, in `w74ParameterKeys()`
(`src/core/w74.hpp`), read by the parser, the serializer and the §5 range check. A
missing or non-number key is `INVALID_BEHAVIOUR_PARAMETER` at parse; an out-of-range one
the same code from validation, on unused behaviours too. Until composition (BA28) a
`w74` behaviour named by any vehicle type or compiled road selection makes Run report
`UNSUPPORTED_BEHAVIOUR_MODEL_RUN`; authoring, save and load accept it. The Driving
behaviours dialog shows a `w74` behaviour read-only (name editable); parameter editing
is a later slice.
